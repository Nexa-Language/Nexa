# Nexa 3.0.0 — Open Programs

Release: [v3.0.0](https://github.com/Nexa-Language/Nexa/releases/tag/v3.0.0). Python 3.10+; Linux/macOS for the Open Programs runtime. Candidate execution requires Docker/OCI. Install the wheel from this GitHub Release; the PyPI project with the same name is unrelated.

```sh
python -m pip install https://github.com/Nexa-Language/Nexa/releases/download/v3.0.0/nexa_lang-3.0.0-py3-none-any.whl
nexa --version
```

Assets include the wheel, sdist, `SHA256SUMS` and a build provenance record. Source archives include the Rust AVM and the reproducible experiment harness.

## A program owns its goals and evidence

Open Programs brings model-assisted compilation, persistent program revisions and conditional implementation reuse into one language contract. A `.nx` program declares typed goals, allowed capabilities and acceptance requirements. People can supply implementations directly; a configured model can fill open implementations. The compiler executes candidates in OCI, records deterministic checks and model reviews separately, and admits only results satisfying the current policy.

`language "3.0"` selects the new frontend. Existing 2.4 source and compiler APIs retain their versioned path. The Python reference implementation supports build and runtime goals, explicit dependencies, typed JSON boundaries, and the repository maintenance handler. See the [core contract](../spec/3.0/core.md) and [usage guide](../spec/3.0/usage.md).

## Implemented workflow

- Offline `check` reports source diagnostics and unresolved goals. `build` resolves declared build goals within a shared call, token and time budget; `build --locked` validates stored artifacts with zero model requests.
- The versioned [author protocol](../spec/3.0/author-protocol.md) supports source revisions, resolution, clarification, events, cancellation and evidence explanation. CLI and author clients share the compiler and persistence model.
- Immutable revisions, content-addressed objects, SQLite transactions and process leases support restart and conflict detection. New activities adopt a revision at a checkpoint; existing activities remain pinned. Unknown external effects require reconciliation.
- Repository maintenance produces a typed patch and an exact diff. Applying it requires a separate grant covering the proposal, selected paths, baseline, policy, evidence, task and expiry. Retained original files and a journal preserve concurrent editor writes and interrupted application.
- Local implementation capsules carry provenance, license, conditions and evidence. Receiving tasks validate compatibility and current evidence. A capsule cannot override an author's explicit implementation.
- A `.nx` diagnostic advice pass can improve compiler diagnostics under a frozen external suite. C1/C2 locked bootstrap compares the pass and corpus outputs. Selecting the candidate requires approval. A separate `3.1-budget` proposal demonstrates versioned syntax, migration and semantic comparison.

## Real model integration and verification

The tested Aliyun binding uses `qwen3.8-max-0902`, `ALIYUN_API_KEY`, and `ALIYUN_BASE_URL`. Configuration stores variable names; keys stay in the provider process. [The successful six-stage run](../../plan/evidence/2026-10-23-open-programs-flagship.json) records 11 requests, 12,075 input tokens and 1,486 output tokens over 46.537 seconds. Recorded responses also support offline replay through real OCI containers. Approval actors in these fixtures represent test authority.

The [experiment harness](../../benchmarks/open_programs/README.md) records fixed synthetic tasks, stage budgets, source hashes, results and failures. With equal output schemas, Open Programs accepted 73/90 stages and the adapted 2.4 baseline 70/90; the no-reuse and no-feedback variants accepted 68/90 and 41/90. [The report](../../plan/evidence/2026-10-23-open-programs-experiment.md) preserves the first round's baseline-schema correction, token totals and limits of the synthetic task set. See the [execution record](../../plan/04-v1-open-programs-execution.md) for the final test environments, audit fixes and validation scope.

## Migration and supported scope

Use the [2.4 migration guide](../migration/2.4-to-3.0.md). Legacy state is read through a read-only SQLite snapshot and exported into an independent inert archive with a conversion report. Legacy approvals and unknown effects never activate a new program automatically.

The initial implementation targets local repository maintenance. Named environment, sandbox and acceptance clauses identify reference bindings; concrete capabilities, checkers and provider settings come from the explicit environment. Candidate execution is offline Python in OCI; models run through the compiler's bounded provider interface. Arbitrary candidate-initiated model or network RPC, remote multi-user authorization, public capsule distribution, full Python stack replacement and complete compiler self-hosting remain outside 3.0.0. The Rust AVM retains its 2.4 subset. External editor applications can consume the documented protocol; their UI releases are separate work.


## Dependency security

The distribution requires AnyIO 4.14.2 or newer (below 5); the development lock retains the tested 4.15.1. This excludes the affected versions in the upstream [TLS hostname advisory](https://github.com/agronholm/anyio/security/advisories/GHSA-82r6-8w77-94w6) and [process-pool stderr advisory](https://github.com/agronholm/anyio/security/advisories/GHSA-5p39-cfhj-2xmp), including installs into an existing environment.
