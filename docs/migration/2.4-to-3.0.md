# Migrating Nexa 2.4 programs and state

Nexa 3.0.0 accepts both explicit `language "3.0"` Open Programs and existing 2.4 sources. Sources without a version declaration retain the 2.4 path. Existing SDK `compile_source` / `compile_file` keep returning Python-lowering compilations; `compile_program` is the version-aware entry point. The 3.0 runtime requires Linux/macOS and an OCI backend; the language and state schemas are explicitly versioned.

## State

```sh
uv run nexa open migrate .nexa/runs.sqlite3 --target .nexa/open-archive.sqlite3
```

The source is opened with SQLite `mode=ro` in a read transaction, including committed WAL contents. The destination must be a new path. Known 2.4 RunState v1 rows become immutable LegacyRunArchive objects in a separate 3.0 database, retaining original state and provenance. The migration report records the logical snapshot digest, imported run IDs, object digests and per-row errors. Unsupported schemas produce errors and keep the source unchanged.

An archive is inert: no active Open Program, tool call or approval is created. `started` tool outcomes become explicit `unknown_effects`, with `resume_allowed=false`. Reconcile these against the original tool/provider before starting new external work. Existing approvals belong to their 2.4 calls and do not authorize 3.0 patches. Keep legacy checkpoints in their original location for the existing 2.4 resume command.

## Source contracts

| 2.4 structure | 3.0 migration |
|---|---|
| Pure function / computation | A goal with typed parameters and a Python `solve(inputs)` or literal implementation; execution moves into OCI |
| Agent prompt | Goal intent plus named deterministic checks and separate review rules |
| Tool exposure / sandbox policy | Explicit goal capabilities and controller-owned adapters; host callbacks need an explicit broker contract |
| `verify` / output Protocol | Type boundary plus frozen OutputCheck or RepositoryCheck cases |
| Sequential flow | Build/runtime goal dependency DAG; dependency results appear in `inputs.dependencies` |
| Source edits during a run | Propose a child source revision, build, then activate at a checkpoint |
| Approval before write | Exact PatchProposal / ApprovalGrant bound to baseline, policy and evidence |
| Session history reuse | Explicit capsule with provenance, implementation conditions and current validation |

The maintenance subset supports Int/Float/String/Bool/Json/Unit and structured Patch/Repository/ChangeRequest boundaries. Arbitrary 2.4 flow control, streaming callbacks, MCP sessions, dynamic tool imports, actors, distributed state and framework integrations need explicit adapters or continued use of the 2.4 entry point. The migration command reports state portability; source translation remains a reviewed authoring task because prompts and tools do not uniquely determine a goal's acceptance contract.

Runtime state migrations between 3.0 revisions execute a pure Candidate under OCI and validate the returned JSON against the target schema. Failed migration preserves the prior runtime head. Source revision CAS and runtime activation are separate, so clients must retain both identities.
