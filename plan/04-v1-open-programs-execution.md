## 接口预检与执行决定

- T0 → T1/T2：统一使用不可变、版本化对象。源码位置属于诊断元数据，规范化语义摘要不受文件移动影响；源码内容摘要另行保存。
- T2 → T3/T4/T5：检查结果、有效性与验收判定分别保存；运行时只接受当前上下文的验收判定。时间由控制器传入，便于重放与过期检查。
- T3 → T4/T8：候选及验证必须走 OCI；测试 transport 可用于故障注入，正式路径不得回退到宿主执行。
- T5 → T6：版本接纳与工作区批准独立。批准对象必须绑定准确补丁、基线、策略与证据。
- T2/T4 → T7：复用生成普通候选；条件匹配与证据有效性使用同一摘要规则。
- T4–T7 → T8：演进验收器、种子编译器和语料固定，候选无权改写正在使用的评价标准。
- 继续在本任务已有的独立功能分支 `feat/nexa-3-open-programs-plan` 实施，保留已批准规划文件；其他生态任务已结束主仓写入。复用 v2.4.0 的未变化基线验证，不重跑相同快照。
- 使用既有 Pydantic 与 Lark，不增加运行依赖。对象按其首个消费者引入，避免预置尚无行为的框架。
- 规范编译入口增加 `compile_program` 做版本路由；保留 `compile_source`/`compile_file` 的 2.4 返回类型，避免既有 SDK/API 消费者因返回类型变化失效。3.0 CLI 使用新的结构化检查报告。
- 3.0 对外发布需单独执行发布计划；本轮不移动 v2.4.0 tag、不更新线上官网为未发布版本。
